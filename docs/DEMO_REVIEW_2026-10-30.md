# OW-DMS 가상자료 시연 결과 및 고도화 방안

작성·시연일: 2026-10-30(KST)

## 1. 결론과 적용 상태

수정 브랜치에서 **가상자료 업무 시연 14단계와 신규기관 설정·후원금 입력 시연을 완료**했다. 설정 → 후원금 초안, 물품 수입 → 승인 → 재고 → 문서, 정정, 통장 반입, 약정 연결이 동작했다. 녹화 영상 2개와 단계별 화면을 별도 산출물 폴더에 보존했다.

다만 시연 통과가 전체 권한·회계·법정서식·운영 준비의 완성을 의미하지 않는다. 추가 확인에서 **물품담당에게 후원금 합계와 승인 스냅샷이 반환되는 권한 범위 문제를 재현**했다. 다음 개발은 새 기능보다 조회·승인 권한 보강을 우선한다.

이번 작업의 고도화 항목은 **추가 개발 제안**이다. 아래 개선안 전체를 구현·배포한 상태가 아니다. 운영 기관 데이터·계정·계좌는 사용하지 않았으며 운영 서버·기관 설정을 변경하지 않았다. 확인 당시 PR #12는 열려 있고 미병합이었다.

## 2. 시연 환경과 데이터

- 기준 코드: 로컬 `b854626` / PR #12 원격 `2a50e9b`와 업무 코드 트리 동일. 이번에 시험 스크립트의 선택적 영상 녹화만 추가.
- 환경: Windows, Node 24.22.1, Next.js 개발 서버, PostgreSQL 16.10, Playwright + 별도 Chrome 시험 세션.
- DB: loopback 전용 신규 합성 시연 DB. 운영 접속정보를 사용하지 않음.
- 기관·사용자: 가상복지관 A/B, 별도 신규 가상기관, 가상 후원/물품/승인/회계/관리 직무.
- 물품: 기존 합성 쌀 100포와 별도 20포 사례. 이번 시연에서 새 20포 입고·승인 후 해당 물량의 20포 반영을 확인.
- 평가 예시: 20포 × 30,000원 = 600,000원. **시가·세무상 확정가액이 아닌 합성 시험값**.
- 후원금: 신규 가상기관에서 100,000원 전액 배분 초안 1건, 60,000원+40,000원 분할 초안 1건.
- 약정: 가상기업 월 50,000원. 약정만 등록했을 때 미납, 초안 연결 후 승인 대기로 확인.

후원금 초안 2건은 승인수입 200,000원을 뜻하지 않는다. 후원품 20포 역거래도 기관의 모든 쌀 재고가 0이 된다는 뜻이 아니라 해당 신규 로트의 입고 효과가 취소되었다는 뜻이다.

| 2 | 쌀 10kg 20포, 예시 단가 30,000원 | 수입 초안 저장 |

| 12 | 동명이인·기업후원·이자 | 동명이인 자동선택 없음, 선택 후 초안 연결, 이자 제외 |

| 14 | B기관으로 재고 조회 | A기관 재고 노출 없음 |

### 신규기관 설정·후원금 입력 시연

1. 시설·기금이 비어 있는 가상기관에서 저장폼 대신 기준정보 등록 안내가 나오는지 확인했다.
2. 가상 운영주체를 등록하고 연무 설정 후보의 소속·기금을 검토해 적용했다. 실제 연무 운영법인명은 입력하지 않았다.
3. 비지정후원금 하나를 선택한 100,000원은 배분액이 자동 입력되고 초안으로 저장됐다.
4. 분할 배분을 60,000원+50,000원으로 입력하면 합계 불일치 안내가 표시됐다.
5. 오류 뒤 금액·시설·기금 선택이 유지됐고, 두 번째 배분을 40,000원으로 고쳐 저장했다.
6. 저장 후 기존 오류가 사라지고 목록에 초안 2건이 보였다. 조회 역할에서는 입력폼이 표시되지 않았다.

브라우저가 실제 데이터를 넣어 저장한 과정이다. 화면 목업을 재생한 결과가 아니다. 다만 비밀번호·OTP·백업복구·공식 외부전송은 이번 녹화 시연 범위에 포함하지 않았다.

## 4. 발견 사항: 재현과 코드 검토를 구분

### F01. 물품담당 조회 범위 보강 필요 — P0 / API 재현

합성 `GOODS_STAFF`는 `money.read` 권한이 없지만 다음 결과를 받았다.

| 점검 | 관찰 |
|---|---|
| `/v1/auth/me` | `money.read` 없음 |
| `/v1/dashboard` | HTTP 200, `monthConfirmedIncome="100000"` 반환 |
| `/v1/approvals` | HTTP 200, 후원금 승인 스냅샷 포함 |

기관 간 RLS와 별개로 **같은 기관 안의 직무별 조회범위** 문제다. 실기관 자료로 시험하지 않았으며, 실제 정보 노출 발생 여부를 단정하는 결과는 아니다. 금액 합계를 화면에서 숨기기만 하는 수정으로는 충분하지 않다.

확인 위치: `packages/db/src/services/dashboard.ts`, `packages/db/src/services/approvals.ts`, `packages/domain/src/permissions.ts`.

개선: 모든 목록·대시보드·문서·마감·정정에서 자원 종류별 읽기권한을 검사한다. 승인요청도 `approval.request`와 대상의 작성권한을 함께 확인한다. 권한 없는 자료는 응답 본문·건수·합계·스냅샷에서 제외한다. 권한 조합에 따른 경로·버튼도 일치시킨다.

인수 기준: 물품담당은 금전 합계·금전 승인본문을 받지 않는다. 회계·영수증담당은 허용된 금전정보만 본다. 후원담당/물품담당/승인권자/관리자/감사의 API·직접URL·파일 접근을 교차검증한다. 기존 기관 격리도 유지한다.

### F02. 일부 화면의 숨은 시설 자동선택 — P0 / 코드 검토

수정한 직접 후원금 입력과 달리 약정 등록·통장 입금 연결·재고 배분은 첫 시설 ID를 숨은 입력으로 사용한다. 시설이 여러 개인 기관에서 잘못된 귀속이 생길 수 있고, 비어 있는 경우 같은 종류의 입력 실패가 남아 있다.

확인 위치: `apps/web/app/(app)/pledges/page.tsx`, `money/import/page.tsx`, `stock/page.tsx`.

개선: 공통 시설 선택 컴포넌트, 빈 기준정보 안내, 선택한 시설에 속하는 창고 필터를 적용한다. 하나면 표시와 함께 선택, 여러 개면 명시적 선택을 요구한다. 서버는 시설·창고·로트 관계도 검증한다.

인수 기준: 시설 0/1/2개, 사용 중지 시설, 다른 시설 창고, 타 기관 ID를 포함한 시험에서 의도한 귀속만 저장된다.

### F03. 초기 설정과 실제 업무 준비의 차이 — P1 / 화면 관찰

연무 후보는 시설·선택 기금을 추가하지만 창고·품목·직원 직무·서식은 자동 완성하지 않는다. 설정 버튼 하나를 누르면 물품업무 전체가 준비됐다고 오해할 여지가 있다.

개선: `소속 → 시설 → 기금 → 창고/품목 → 담당/승인권자 → 양식 검토`의 준비 체크리스트를 보여준다. 실제 항목이 없는 경우 빈 목록 대신 다음 조작을 안내한다. 직원·원장·가액을 임의 생성하지 않는다.

### F04. 건수 제한이 통계로 오인될 가능성 — P1 / 코드 검토

약정 목록은 최대 500건을 읽고, 미납 약정 수는 이 목록에서 계산한다. 자료가 500건을 넘을 때 전체 미납 수와 다를 수 있다. 목록 제한이 있다는 이유만으로 운영 규모가 이미 이를 초과했다고 단정하지 않는다.

개선: 전체 집계와 페이지 목록을 분리한다. 서버 검색·기간·시설 필터, 커서/페이지, 총건수·표시건수, 페이지 다운로드 범위를 명시한다.

인수 기준: 합성 약정 501건 이상에서 전체 집계가 정확하고 페이지 변경·필터로 정상 자료가 누락되지 않는다.

### F05. 모바일 표와 오류 복구의 일관성 — P1 / 화면·코드 검토

후원금 직접 입력은 이번 수정에서 오류 후 값이 유지되지만, 다른 폼은 오류 쿼리로 이동하는 방식이 남아 있다. 모바일은 가로 스크롤 표 구조로 업무 확인이 가능하나 열이 많아 조회·입력에 이동이 필요하다.

개선: 폼 공통 상태·한국어 필드오류·저장 중 표시·재전송 방지·입력 유지, 모바일 카드형 요약과 상세보기, 스크린리더 오류 안내를 도입한다. 입력 원문을 URL·로그·브라우저 영구저장소에 남기지 않는다.

| 사업·기금 | 사업코드, 기금ID, 기탁목적, 사용기간, 제한조건, 귀속주체ID | 표시명만으로 법인/시설 귀속을 추정하지 않음 |
| 결연 지원 | 제한된 대상자ID, 지원월, 계획액, 승인액, 지급확인, 지급증빙참조 | 실명·상담내용 최소화, 실제 송금과 문서 생성을 구분 |
| 후원품 | 입고로트, 품목, 단위환산, 보관장소, 유효기한, 가액상태, 배분목적, 수령확인 | 재고·평가액·세무가액을 동일시하지 않음 |
| 모금함/저금통 | 비개인 설치처ID, 회수일, 회수액, 입금거래참조, 검수자 | 예금주 표시로 실제 후원자를 자동 확정하지 않음 |
| 행사/외부지원 | 행사/사업ID, 계획·결과, 총액·비용·순액, 정산상태 | 후원금인지 사업수입인지 회계 확인; 자동 후원처리 금지 |
| 문서 | 문서유형, 결재/검토상태, 서식버전, 원거래·출력해시 | 내부 확인서와 세무·행정 법정서식을 구분 |

이는 설계 후보이며 새 테이블·법규 규칙·기관 확정 입력값을 이번 작업에서 운영 적용한 것은 아니다. 실제 계좌번호·기부자 세무식별번호는 일반 메모 필드로 추가하지 않는다.

## 7. 권장 개발 순서

1. **다음 수정 묶음:** H01 권한범위 → H02 시설 선택·준비 점검. 재현된 문제를 회귀시험으로 고정하고 API·UI를 함께 수정한다.
2. **그다음 실무 묶음:** H03 영수증 발급 준비 → H04 기금·전표 대조 → H09 마감 작업함. 현금흐름과 발급대상을 검산할 수 있게 한다.
3. **기관 맞춤 묶음:** H06 물품 세부거래 → H07 기관양식/PDF → H08 정산파일. 개인정보 없는 실제 규격 샘플과 기관 검토가 필요하다.
4. **운영·확장 묶음:** H05 대량약정, H10 보존·파기, H11 소통관리. H12는 근거·시험 확보 시 작업별로 활성화한다.

한 번에 화면을 많이 추가하기보다 `입력→검증→승인→원장→대조→문서→정정`이 끝나는 한 업무씩 완성한다. 각 묶음은 합성자료 회귀시험과 담당자 사용검토 후 종료한다. 인력·기관검토·외부규격에 따라 일정이 달라지므로 이 문서에서는 확정 일정을 제시하지 않는다.

## 9. 재현·녹화 방법

기존 `tests/browser/smoke.mjs`와 `tests/browser/money-setup-smoke.mjs`에 선택적 `DEMO_VIDEO_DIR` 녹화를 추가했다. 설정하지 않으면 기존 점검만 수행한다. Playwright의 녹화 구성요소가 필요하다.

로컬 합성 DB를 준비하고 API·web·worker를 실행한 후 `WEB_URL`, 필요 시 `BROWSER_CHANNEL`, `SHOTS`, `DEMO_VIDEO_DIR`을 설정한다. 신규기관 시험은 loopback의 `*_browser` DB에만 `TEST_SETUP_DATABASE_URL`을 설정한다. 운영 URL·실제 기관 자료를 넣지 않는다. 합성 seed가 있는 깨끗한 시연 DB에서 실행한다.

이번 녹화는 자동화된 기능 시연이다. 실제 직원 사용성 인터뷰·입력시간 측정·1GB 운영 서버 부하시험·장애복원·기관 법정양식 검증을 대신하지 않는다.
